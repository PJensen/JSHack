# Session Notes — 2026-04-12

## What We Set Out To Do

Make combat feel more visceral. The playtest (4/10) flagged balance as too generous and TTK as spongy. The initial idea was **multi-attack** (NetHack-style claw+bite+tail per monster turn).

## Multi-Attack Attempt (reverted)

Added `extraAttacks` arrays to monster definitions with per-attack dice, chance, damage type. Extra attacks were gated by speed stat and rolled independently. Mechanically worked — but visually illegible. All hits landed in the same frame as a damage spike, not as distinct sequential attacks. Reverted.

**Lesson:** The problem isn't the combat system — it's the tick model. All monsters resolve simultaneously in one `world.tick(1)` call.

## Sequential Monster Turn System (stashed as `sub-tick-resolve`)

Built a fused AI+movement system that processes each monster one at a time within the same tick.

### Architecture

**New file:** `src/rules/systems/monsterTurnSystem.js`
- Replaces `aiChaseSystem` + `aiScurrySystem` + `aiFlyingSystem` in the scheduler's `ai` phase
- Builds a queue of enemy monsters sorted by speed (fastest first)
- For each monster: runs AI (emit intent) then resolves movement/combat inline
- Uses shared `blocking` Set and `tiles` snapshot across the loop
- Propagates monster destinations into `tiles.blockedByCell` so `movementSystem` (player) sees correct positions later in the same tick

**Refactored files:**
- `aiChaseSystem.js` — extracted `runChaseAI(world, id, ctx)` and `buildChaseAIContext(world)`; exported `ACTIVE_RADIUS`
- `aiScurrySystem.js` — extracted `runScurryAI(world, id)`
- `aiFlyingSystem.js` — extracted `runFlyingAI(world, id, playerCtx)`
- `movementSystem.js` — extracted `resolveSingleMove(world, actor, intent, tiles, blocking)`; added `tiles.blockedByCell.add(k)` propagation on successful moves

**Display stagger:** Added `monsterTurnIndex` (Symbol-keyed on world, incremented per monster in the queue). Stamped on `damaged` events via `dealDamage.js`. `goreEngine.js` uses it to stagger float text and gore particles by 120ms per monster.

**Scheduler change:** `monsterTurnSystem` registered in `ai` phase, replacing the three separate AI systems. Non-combat AI (townfolk, farm animals, pets) unchanged.

### Status

All 1868 tests pass. Rules-layer sequential processing is correct. **Stashed because 120ms VFX stagger wasn't visually legible** — attacks still felt simultaneous. The display pacing problem remains unsolved.

### Open Display Pacing Ideas

- Larger stagger (200-300ms)
- Per-attacker hitstop (brief frame pause between monsters)
- Input gating (block player input for N ms per monster that attacked)
- Animate the attacker's lunge/bump BEFORE dealing damage
- The rules layer is solid — only the display layer needs work

## Equipped Array Simplification (committed)

Removed redundant `{ slot, itemId }` objects from monster `equipped` arrays. Slot is now inferred from the item catalog via `inferSlotFromItemId()`. Ammo items (not in equipment catalog) are detected by `ammo_` prefix.

**Before:** `{ slot: "armor", itemId: "chain_armor" }`
**After:** `"chain_armor"`

Only exception: ammo could theoretically still need `{ slot: "ammo", itemId: "ammo_arrows" }` but the prefix detection in `spawnMonsterEntity.js` handles plain strings now too.
