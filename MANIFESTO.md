JSHack is not just a project. It is a refusal.

It begins with a simple disgust: the sense that too much of modern software arrives already owned. Not merely by license, but by assumption. By framework. By institution. By ambient pressure. You are told you are free to build, but the freedom is pre-shaped. The roads are laid down in advance. The vocabulary is chosen for you. The architecture is implied before you write the first line.

Use React, and Meta is in the room.
Use TypeScript, and Microsoft is in the room.
Use the modern package ecosystem, and ten thousand upstream strangers are in the room with their abstractions, churn, preferences, and assumptions about how software ought to be made.

This is presented as convenience. Sometimes it is. But it is also enclosure.

That is the deeper crime. Not complexity alone. Not bloat alone. Enclosure. The slow conversion of programming from direct authorship into supervised participation inside systems built by others. Forced languages. Canonical frameworks. Dependency cathedrals. Libraries hoisted upon you before you have even touched the actual problem. The whole industry leaning over your shoulder, teaching you to think in approved forms.

And beyond that: the cloud. The great enclosure of computation itself.

The machine used to be yours. Then it became rented. Then remote. Then abstract. Then governed by APIs, platforms, billing dashboards, registries, and invisible revocation powers. Your software no longer ran on a machine you possessed so much as in a territory you temporarily occupied. Computing became tenancy. You could build there, yes—but only through gates, under terms, inside someone else's perimeter.

JSHack pushes the other way.

The agents didn't make JSHack easier. They made it possible.

Seventy-two systems. One hundred and five components. Three hundred and sixty-three items. A weather simulation, a lunar calendar, a town economy, a deity pantheon, a dungeon generator, particle VFX, procedural Perlin noise terrain, proc trees, a crafting bench, a hunger clock, a combat system with dual-wielding and affix modifiers — one hundred and thirty thousand lines of plain JavaScript, all of it deterministic, all of it in open air. No human could have typed this alone at this depth in this timeframe without either surrendering the constraints or surrendering the ambition.

The bottleneck in solo projects was never ideas. It was that holding the vision and typing the implementation compete for the same hours and the same mental registers. By the time you've wired the fortieth system, you've half-forgotten the intent behind the twelfth. The detail erodes the design, or the design starves the detail.

What happened here is that the detail layer became collaborative without the architecture becoming committee. The deterministic RNG, the event-driven ECS discipline, the three-layer separation — those held because they lived in one mind the whole time. The agents didn't negotiate them. They inherited them. Seventy-two systems that all obey the same conventions isn't just a lot of code. It's proof that the conventions were clear enough to transmit and rigid enough to survive contact with implementation at scale.

That's the part that was hard. That part was human.

It is an attempt to recover software as something direct, inspectable, and human-scale. A place where code is not translated into some other shape before it can live. A place where JavaScript is allowed to remain JavaScript. No npm. No webpack. No Babel. No TypeScript. No dependency pile. No build step. Just ES modules, real files, a static server, a browser, and the nerve to believe that is enough.

Serve the folder.
Open the page.
Edit a file.
Refresh.
The change is there.

That is not just a workflow improvement. It is a philosophical statement.

It means the project does not pass through a gate before it becomes real. There is no priesthood standing between the source and the thing itself. No compiler ceremony. No bundler fog. No industrial packaging ritual where the original code disappears into a machine and emerges as an artifact only half-related to what you wrote. The code the builder touches is the code the machine runs. The files remain themselves. The ideas remain legible.

That is why the release question matters.

Most software is hidden by default. Most code lives behind a curtain. The user touches behavior, not source. They interact with the artifact, not the body. That is the normal proprietary arrangement.

But a browser game written this way is different.

JSHack does not ship as an opaque lump. It does not disguise itself as an industrial artifact. It ships as the thing it is: JavaScript modules, plainly served, plainly inspectable. The player is not merely consuming the game. The player is receiving the mechanism. The source is not somewhere else. It is right there, in open air.

Could it be taken private? Legally, yes.
Should it be? No.

Because in a project like this, closure would not merely be a licensing choice. It would be a contradiction. JSHack's whole thesis is anti-enclosure. Anti-gate. Anti-priesthood. Anti-obscuring pipeline. To build a system around transparency, inspectability, directness, and hackability, and then retreat into concealment, would be to violate the work at the level of first principle.

That does not mean the surrounding ecosystem is innocent. It is not. It is extractive. It absorbs whatever it can. It repackages, ingests, centralizes, rehosts, rebrands, and monetizes. So the point is not to pretend that all downstream uses are equally honorable. The point is to keep the code visible without surrendering the meaning of the act.

The license is not paperwork. It is the political border of the work.

JSHack must be open because the medium invites openness.
It should be open because the philosophy demands it.
But it cannot be innocently open because the surrounding order is predatory.

That tension is real. It is central.

Every line was written by agents. That changes less than people think. The decisive question is whether machine-produced code lands inside a transparent system or an enclosed one.

JSHack is an argument for the transparent one.

A future built from generated code does not have to become more obscure, more corporate, more remote, more priest-ridden. It can go the other way. It can produce artifacts that are simpler, plainer, more inspectable, and more easily modified by the people who receive them. JSHack is an argument for that path.

It rejects forced software language.
It rejects inherited stack theology.
It rejects cloud tenancy as the final form of computing.
It rejects dependency feudalism.
It rejects the idea that the builder must think in shapes handed down by larger powers.

And beneath all of that, it defends something older and simpler: when you build a thing, the thing should still feel like yours. Not because no one else can see it, but because it still bears the shape of your judgment. Because it has not been passed through an institutional filter before it was allowed to live. Because it has not been turned into ceremony. Because the files still sit there, intact, honest, waiting for anyone curious enough to open them.

JSHack is that honesty, defended.

Not hidden.
Not rented.
Not blessed by gatekeepers.
Not obedient to the stack.
Not bundled into fog.
Not enclosed.

Just there.

A living program, served plain.
